One MessagePack encoding for Tox protocol messages and stored data, defined by
Haskell types and checked for compatible changes.

# Objective

We want to use MessagePack for more of the Tox protocol and for data we store.
This design proposes one encoding for all of it, with formats defined as
Haskell types (for now, see [Alternatives](#other-sources-for-the-schema) for
later). From one derivation of those types we get the encoder, the decoder and
a schema, so the three can't disagree. Other languages use the schema, and we
use it to check that a change to a format doesn't break older versions.

The goals are:

1.  Small messages.
2.  No hand-written decoders. Every length is checked before allocating.
3.  Formats can change without breaking older versions.
4.  Equal values encode to equal bytes, so we can hash and sign them.

Non-goals:

- Encryption and signing. Those stay as they are.
- Moving every existing packet to MessagePack at once. A format moves when we
  next change it.
- A neutral schema language. For now, the Haskell types are the schema.

# Background

MessagePack is already used in several places, each in its own way:

- c-toxcore writes its events as MessagePack (`tox_events_get_bytes`). The
  code in `toxcore/events/` is generated by `other/event_tooling` from event
  descriptions written in C++.
- c-toxcore reads and writes saved group chats by hand with `bin_pack` and
  `bin_unpack` (`group_pack.c`).
- Rust's `tox-proto` derives the code from Rust types, following the rules in
  `rs-toxcore-c/tox-proto/ENCODING.md`. Account sync uses it.
- hs-toxsync reads and writes account sync messages by hand
  (`Tox.Sync.MessagePack`), following the same rules. It already handles
  fields added later (`laterFlag`), fields it doesn't know (`end`, `carry`)
  and unknown enum tags (`variant`, `lenient`). tox-proto's `Kept` does the
  same in Rust.
- hs-toxcore derives its instances with `msgpack-types`
  (`Tox.Persistence.Nodes`). This library writes a record with one field as the
  bare field, where tox-proto writes `[field]`, and has no instance for
  `Maybe`.

A hand-written conformance suite keeps the Rust, Haskell and Dart
implementations of account sync in agreement.

hs-schema derives a schema from Haskell types and generates C structs with
getters and setters from it. It was meant to generate c-toxcore's events, but
it doesn't read or write MessagePack, and nothing uses it yet.

So each implementation defines the format again. Hand-written decoders are
where length and bounds mistakes happen, and only review checks that a change
keeps older versions working.

# Requirements

A field should cost little more than its value.

Readers must check every type, and every claimed length against a limit,
before allocating anything. Every byte string, text and list has a maximum
size, and so does every message.

Every message must be readable on its own. We store, forward and relay
messages, and send them to groups.

A format must be able to change in the ways listed under [Changing a
format](#changing-a-format) without breaking older versions in either
direction. CI must report any other change.

Code generated for C must only need c-toxcore's `bin_pack` and `bin_unpack`.

# Design Ideas

The rules mostly follow what c-toxcore's events, tox-proto and hs-toxsync do
already.

## Values

| Haskell type        | MessagePack                                   |
| ------------------- | --------------------------------------------- |
| `Bool`              | `true` or `false`                             |
| `Word8` .. `Word64` | unsigned integer, shortest form               |
| `Int8` .. `Int64`   | integer, shortest form                        |
| `ByteString`        | `bin`, at most its declared size              |
| `FixedBytes n`      | `bin` of exactly `n` bytes                    |
| `Text`              | `str`, valid UTF-8, at most its declared size |
| `[a]`               | array, at most its declared length            |
| `Maybe a`           | `nil`, or the value                           |
| record              | array of its fields, in order, even for one   |
| `newtype`           | the field itself                              |

A `newtype` can't gain fields, so it's written as its field. A record is always
an array, so it can gain fields at the end.

Integers carry their own size in MessagePack, so a reader of a `Word32` field
accepts any unsigned integer that fits, and a field can later become wider
without changing its bytes.

`Maybe (Maybe a)`, or a `Maybe` of anything else that can be `nil`, would be
ambiguous. We don't use it, so the schema rejects it for now.

Text from peers, such as names and messages, is a `ByteString`. A peer may send
invalid UTF-8, and we keep it as it came. We use `Text` only for values our own
code writes.

Fixed-size byte fields next to each other, such as a public key and a nonce,
can be written as one `bin`, as tox-proto's `#[tox(flat)]` does. This saves the
header of each field.

## Sums

A constructor without fields is written as its bare tag, a constructor with one
field as `[tag, field]`, and a constructor with several fields as `[tag,
[field, ...]]`. Tags count from 0 in the order of the constructors.

A constructor can't go from one field to several without breaking older
readers. A constructor that may gain fields holds one record, as each of
c-toxcore's events does, and the record grows at the end.

Each sum type says what a reader does with a tag it doesn't know:

- Reject the value.
- Skip it. This suits lists, where the other values are still useful.
- Keep its bytes and write them back unchanged, as tox-proto's `Kept` does.
  This suits data we store or pass on.

## Changing a format

A field is identified by its position. These changes keep older versions
working:

1.  Adding a field at the end, with a default. A reader fills in the default
    when the field is missing (the writer is older) and skips fields after the
    ones it knows (the writer is newer).
2.  Retiring a field. From then on it's written as `nil`. This costs one byte
    and keeps later fields in place.
3.  Adding a constructor at the end of a sum, if the sum's rule for unknown
    tags lets older readers cope.
4.  Widening an integer field.
5.  Renaming anything. Names don't go on the wire.

Everything else breaks older versions: reordering fields or constructors,
removing them, inserting them anywhere but at the end, and changing a field's
type.

A program that changes a value written by a newer version keeps the trailing
fields it doesn't know, as hs-toxsync's `carry` does.

A record with many optional fields that are mostly unset can end with a map
from small integer keys to the fields that are set, instead of writing a `nil`
for each. We only do this where it saves bytes.

## Schema

The schema is a data structure of its own (hs-schema's `Schema`). The
generators and the checker only read the schema, so another source can produce
it later. Sizes, versions, retired fields and rules for unknown tags are part of
the schema, not only of the Haskell types.

## Haskell types

The first source of schemas is Haskell types deriving `Generic`, with wrapper
types for what `Generic` can't say:

- fixed sizes (`FixedBytes n`) and maximum sizes (`MaxBytes n`,
  `MaxList n a`);
- the version a field was added in, with its default;
- retired fields;
- each sum type's rule for unknown tags.

Types for Tox's own protocol, such as save data, live in hs-toxcore. Protocols
in layers above Tox live in their layer's library, such as account sync in
hs-toxsync.

c-toxcore's events are the exception. Their types come from `tox_events.h`, the
public API: apigen already generates them in Haskell, and will generate their
codecs too.

hs-schema will derive the encoder, the decoder and the schema together. Today
`ToSchema` and `msgpack-types`' `MessagePack` are derived separately, so
nothing keeps them in agreement.

## Checking changes

A checker compares a format's schema with that of its last release and reports
every change the rules above don't allow. CI runs it.

## Other languages

For C, hs-schema will generate the reading and writing code with `bin_pack` and
`bin_unpack`, as `other/event_tooling` does for the events now.

The events are the first test. Their codecs, from the types apigen generates,
must read and write the same bytes as c-toxcore (`tox_events_get_bytes`), which
hs-toxcore-c's tests check. Events with one field change from `[type, field]` to
`[type, [field]]`.

For Rust and Dart, hs-schema will first generate test cases, like account
sync's conformance suite, for their code to pass. We decide whether to generate
their code too once C works.

# Alternatives Considered

## Doing nothing

Each language keeps its own code for the encoding, and conformance suites and
review keep them in agreement. Every hand-written decoder is another chance to
get a length wrong, and only review checks changes to a format.

## Maps with field names or numbers

Records could be maps keyed by field name, or by field number as in Protocol
Buffers. A key makes adding and removing fields easier, but costs a string or a
byte per field. Positional records with the rules above do the same without
keys, and the trailing map covers records with many optional fields.

## Negotiating field numbers

Peers would agree at the start of a session on a small number for each field
name. A small number costs one byte whether agreed on or fixed, and positional
records need none, so nothing is saved. Messages would also be unreadable
without the session's table. This rules out storing, forwarding and relaying
them, and a group would need a table for every pair of peers. The schema
already gives out the numbers, and a protocol that needs to know what a peer
understands can exchange capabilities.

## Other sources for the schema

Later, we want schemas that don't depend on one language's types: a description
file, protobuf-like or in a format of our own. Such a file suits people working
in other languages, but needs a language and a parser. Protobuf's syntax is
built around numbered fields and has no size limits, so it would need bending.
Our own format could start from the text hs-schema already prints (`schema
1.0; ...`). We start with Haskell types because hs-schema already derives
schemas from them.

# Open Questions

- Should readers reject integers not written in their shortest form? Writers
  already use the shortest form, but c-toxcore's and hs-toxsync's readers
  accept others. This matters where bytes are hashed or signed.
- Which description format do we add later: protobuf-like, or our own?
